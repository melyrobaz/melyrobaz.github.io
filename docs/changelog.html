Le numéro de version du plugin ne sert à rien à l’hôte

PluginV1.version est déclaré et compilé, mais l’hôte ne l’affiche pas, ne le compare pas et ne le journalise pas. Deux DLL du même id avec des versions différentes sont départagées par l’ordre de scan, pas par ce champ. La version affichée dans le site (2.6.0) est celle de l’application, pas celle d’un plugin.

Compatibilité et mise à jour

  • ABI stricte. L’hôte refuse toute valeur différente de 1 avec le message ABI <n> alors que l'hôte attend 1. Aucune tolérance N−1.
  • Structures #[repr(C)]. Ajouter, retirer ou réordonner un champ sans changer ABI_VERSION est un comportement indéfini, pas une erreur détectée.
  • Pas de mise à jour automatique. Une DLL installée doit être remplacée manuellement, application fermée. Le scan n’a lieu qu’au démarrage et Windows verrouille le fichier chargé.
  • Pas de signature ni de bac à sable. La provenance du fichier est la seule protection réelle.
  • Pas de manifeste. Les métadonnées sont compilées dans la table ; un fichier annexe n’est jamais lu.

Historique et politique non disponibles

  • Aucun changelog produit complet de FloralPlayer : les versions antérieures à 2.6.0 ne sont pas documentées ici.
  • Aucun historique Git, aucun tag et aucune note de release dans le dépôt : les dates proviennent de documents de portage, pas d’un registre de publication.
  • Aucun journal des versions de l’ABI : on ne sait pas si une ABI v0 a existé, ni ce qu’elle contenait.
  • Aucune politique de dépréciation pour une future ABI v2, ni de date de fin de support de v1.
  • Aucun changelog des plugins discord et listenbrainz au-delà de leur champ version = "1.0.0", que l’hôte ignore.
  • Le statut futur de seeked, de FLAG_HAS_UI et des panneaux n’est pas défini dans le code.

Maintenir cette page

Quand l’hôte change de version, mettez à jour js/config.js en premier : le numéro se propage au en-tête, au pied de page et aux badges qui portent data-version. Vérifiez ensuite les valeurs lues dans le code, pas les anciens documents.

  1. Configurer le site

    siteName, version, abiVersion, githubUser, repo et released dans js/config.js.

  2. Vérifier le contrat

    ABI_VERSION, la table PluginV1, les callbacks HostApi et la macro declare_plugin! dans ember-plugin-api/src/lib.rs.

  3. Vérifier les plugins livrés

    Contenu réel de ember-sdk/plugins/, champs id, version, category et flags de chaque table.

  4. Mettre à jour les écarts

    Ajouter une ligne datée dans ce journal et corriger les pages concernées. Ne supprimez pas un écart sans avoir relu le code qui le contredit.
