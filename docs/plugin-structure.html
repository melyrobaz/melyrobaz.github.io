Structure et cycle de vie

Où placer une DLL, quand elle est chargée, dans quel ordre ses méthodes sont appelées, sur quel fil, et ce qui se passe quand elle échoue. Cette page décrit le comportement observé dans le noyau de FloralPlayer 2.7.0.

Plugins livrés avec le SDK

Le workspace ember-sdk se compile et contient trois plugins d’exemple : hello, discord et listenbrainz.

Scan et installation

L’hôte scanne exactement deux dossiers, une seule fois au démarrage, dans cet ordre :

  1. <dossier de l'exécutable>\plugins — prioritaire ;
  2. %APPDATA%\Floral Player\plugins.
DÉMARRAGE
  Host::new()
    rotate_log()                 supprime plugins.log si > 1 000 000 octets
    lecture de ember-slint.json  section plugins uniquement
    builtin()                    Paroles, Visualiseurs
    scan <exe>\plugins           DllPlugin::load pour chaque *.dll (trié)
    scan %APPDATA%\Floral Player\plugins
    doublons d'id                ignorés, premier chargé gagnant
    calcul de enabled            plugins.<id>.enabled, sinon FLAG_DEFAULT_ON
    EMBER_PLUGINS_OFF            force false en mémoire
Dossier correct selon le contexte
ContexteDossier scanné
Binaire distribué, exe dans Ember Player\Ember Player\plugins\
cargo run ou binaire debugEmber Player\target\debug\plugins\
cargo build --releaseEmber Player\target\release\plugins\
Toujours, indépendamment de l’exe%APPDATA%\Floral Player\plugins\

Le dossier de données est créé par l’hôte, mais pas son sous-dossier plugins :

New-Item -ItemType Directory -Force "$env:APPDATA\Floral Player\plugins" | Out-Null
Copy-Item ".\mon_plugin.dll" "$env:APPDATA\Floral Player\plugins\"

Tout fichier *.dll est examiné, sans scan récursif. Le nom du fichier est libre. L’identité vient du champ id de la table. Un identifiant déjà chargé — y compris un builtin comme lyrics — fait ignorer l’entrée suivante et écrire une ligne dans le journal.

build.ps1 copie au mauvais endroit

ember-sdk/build.ps1 utilise %APPDATA%\Ember Player\plugins ou Ember Player\plugins. Aucun des deux n’est scanné : l’hôte utilise Floral Player et le dossier de l’exécutable, pas celui du crate. Copiez manuellement vers l’un des dossiers réels ci-dessus.

Cycle de vie

ACTIVATION
  create()                     instance opaque
  init()                       0 = OK, 1 = refus, 2 = panique

EN COURS D'EXÉCUTION (fil UI)
  tick(snapshot)               ~5 Hz, même à l'arrêt
  event(json)                  track_started, played, paused, resumed, stopped
  ui_command(json)             réservé à discord et listenbrainz

DÉSACTIVATION
  shutdown()                   si init a réussi
  destroy()                    l'instance est libérée
                               PAS de FreeLibrary : la DLL reste chargée

FERMETURE
  shutdown() de tous les plugins actifs
  save_settings()
  drop de l'hôte → FreeLibrary

L’activation à chaud et le démarrage suivent le même ordre, mais l’échec n’est pas traité de la même façon :

MomentSi init échoue
Démarrage (boot)Le plugin passe à enabled = false en mémoire, un toast est affiché, rien n’est persisté immédiatement.
Activation par l’utilisateurLe plugin repasse à false, l’état est persisté et le toast annonce l’échec.

Dépendances

deps contient des identifiants séparés par des virgules. deps_ok vérifie seulement que chaque dépendance est activée. Les plugins sont initialisés dans l’ordre alphabétique de leur id, pas dans l’ordre de déclaration ni dans un ordre topologique.

  • Aucune détection de cycle.
  • Une dépendance à soi-même est satisfaite.
  • Au démarrage, une dépendance absente ou désactivée fait ignorer le plugin silencieusement : pas de toast, pas d’init, pas de persistance.
  • Désactiver une dépendance ne désactive pas les dépendants.
  • À l’activation à chaud, l’échec est visible : dépendances inactives.

Fils d’exécution

Tous les appels hôte → plugin se font sur le fil de l’interface :

  • tick est appelé par un timer Slint de 200 ms ;
  • les bascules viennent des callbacks Slint, donc du fil UI ;
  • shutdown final est appelé après ui.run(), sur le fil principal.

Ne bloquez jamais, ne rappelez pas Host depuis un fil

Il n’existe ni thread de plugin côté hôte, ni pool, ni timeout, ni file de travaux. Une boucle infinie ou un appel réseau bloquant dans tick fige l’interface. Le pointeur Host n’est pas Send : un fil créé par le plugin doit renvoyer ses résultats par un canal, et c’est tick qui vide ce canal. 

use std::sync::mpsc::{channel, Receiver, Sender};

struct MonPlugin {
    tx: Option<Sender<String>>,
    rx: Option<Receiver<String>>,
}

// init   : (tx, rx) = channel(); self.tx = Some(tx); self.rx = Some(rx);
// event  : self.tx.clone().unwrap().send("résultat".into());
// tick   : while let Ok(msg) = self.rx.as_ref().unwrap().try_recv() { host.toast(&msg); }
// shutdown: self.tx = None; self.rx = None;

Le pont de l’hôte est protégé par un Mutex, mais l’ordre des actions n’est plus garanti hors du fil UI. La règle pratique reste : ne déplacez que des données pures ou un Sender, jamais Host.

Persistance et réglages

Tous les réglages sont dans un seul fichier : %APPDATA%\Floral Player\ember-slint.json. Chaque plugin possède un objet plugins.<id> : 

{
  "plugins": {
    "hello": { "enabled": true, "runs": 3 },
    "discord": { "enabled": false },
    "mon-plugin": { "enabled": true, "runs": 1 }
  }
}
  • À chaque appel, l’hôte clone l’objet du plugin, exécute la méthode, récupère l’objet modifié et ses actions. Une DLL ne voit jamais les réglages d’un autre plugin.
  • set_setting est visible immédiatement dans le même appel, mais n’est écrit sur le disque qu’au prochain save_settings.
  • save_settings est appelé lors des bascules, de la fermeture et de nombreux réglages d’interface. Il n’y a pas d’écriture périodique dédiée aux plugins.
  • Un arrêt brutal peut perdre les dernières valeurs. Une écriture disque non atomique peut laisser un JSON tronqué en cas de crash.
  • Le fichier contient aussi did (Discord), lbt (ListenBrainz) et slp (Soulseek) en clair, sans DPAPI ni keychain.

Journal

Fichier : %APPDATA%\Floral Player\plugins.log. Format : 

[<unix>] <niveau> [<id>] <texte>

Exemple :

[1761571200] info   [hello] hello : init
[1761571205] debug  [hôte] panneau « browser » : {"id":"browser","lines":["…"]}
[1761571210] erreur [hôte] C:\…\mauvais.dll : symbole ember_plugin_v1 absent
NiveauTagUsage
0infoCycle de vie, informations utilisateur.
1debugTraces fines, panneaux, commandes inconnues.

Le fichier est ouvert en ajout à chaque ligne. Au démarrage, rotate_log supprime le fichier s’il dépasse 1 000 000 octets : pas d’archivage. Les paniques dans tick/event, les messages d’Err d’initialisation, les JSON invalides et les erreurs d’écriture de réglages ne sont pas journalisés.

Modèle de confiance

Une DLL est chargée par LoadLibraryW dans le processus de l’hôte. Il n’existe :

  • aucun bac à sable, aucun processus séparé ;
  • aucune signature ni vérification d’éditeur ;
  • aucun manifeste de permissions ;
  • aucune limite d’accès aux fichiers, au réseau, au registre ou aux API Win32 ;
  • aucun contrôle de provenance.

Ce que l’hôte protège

  • catch_unwind autour des méthodes du plugin et des callbacks hôte.
  • Vérification des pointeurs nuls.
  • CString::new avant chaque envoi : un NUL fait ignorer l’appel.
  • Mutex sur le pont JSON.
  • Vérification stricte de abi_version.

Ce qui reste possible

  • Lire les réglages, les jetons et tous les fichiers accessibles au compte.
  • Ouvrir des sockets et envoyer des données.
  • Figer l’interface par une boucle ou un appel bloquant.
  • Faire planter le processus par un défaut natif.
  • Écrire dans ember-slint.json ou corrompre des données.

La DLL doit aussi avoir la même architecture que l’hôte. Aucun contrôle n’est fait : une DLL x86 dans un hôte x64 échoue dans LoadLibraryW avec l’erreur système 193, présentée comme « chargement impossible ». Les dépendances natives de la DLL ne sont pas copiées et aucun AddDllDirectory n’est appelé.

Remplacer, retirer, réinitialiser

OpérationProcédure
Mettre à jourFermer FloralPlayer, remplacer la DLL, relancer. Pas de rechargement à chaud ; la DLL reste verrouillée jusqu’à la fin du processus.
RetirerFermer l’application, supprimer la DLL. L’entrée plugins.<id> reste dans le JSON, sans effet.
RéinitialiserFermer, supprimer l’objet plugins.<id> (ou le fichier entier), relancer.

Ce qui n’est pas fourni

  • Aucun manifeste, mécanisme d’installation ou désinstallation propre n’existe pour les plugins.
  • Aucune signature de code ni empreinte publiée pour les DLL.
  • Aucun test du chargeur, du pont ou du cycle de vie.
  • Les dossiers hello et remote sont absents alors qu’ils sont déclarés dans le workspace.
  • La politique de compatibilité et de support de l’ABI v1 n’est pas écrite.
