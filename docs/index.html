Écrire un plugin pour FloralPlayer

Le lecteur charge des DLL qui implémentent un contrat C stable, l’ABI v1. Cette documentation décrit ce contrat tel qu’il est réellement implémenté dans FloralPlayer 2.6.0 : points d’entrée, données JSON, cycle de vie, persistance, erreurs et limites.

Source de vérité

Cette documentation a été rédigée en lisant le code du projet, pas en recopiant DocPlugin.html ni ember-sdk/README.md. Quand ces anciens documents contredisent le code, c’est le code qui fait foi. Les écarts vérifiés sont signalés au fil des pages et récapitulés dans le changelog.

Deux familles de plugins

FloralPlayer connaît deux mécanismes distincts. Ils partagent l’onglet Préférences → Plugins et le même espace de réglages, mais pas le même contrat de programmation.

Les types Meta, Ctx, Event, Action et Category du noyau ne sont pas exportés par le SDK. Une DLL ne peut pas les utiliser. Le trait ember_plugin_api::Plugin n’a pas de méthode meta() : les métadonnées d’une DLL vivent dans la table PluginV1.

Ce que l’ABI permet — et ce qu’elle ne permet pas

Disponible

  • Lire la position, la durée et l’état lecture/pause à chaque tick.
  • Recevoir les changements de piste et les écoutes validées.
  • Piloter lecture, pause, arrêt, seek, volume, sourdine, piste suivante/précédente.
  • Lire et écrire des réglages persistants propres au plugin.
  • Afficher un toast et écrire dans le journal.
  • Faire du réseau ou lire des fichiers avec les crates du plugin, sans sandbox.
  • Exporter une commande remote-url pour l’interface.

Indisponible

  • Accéder aux échantillons audio, à la bibliothèque ou à la file d’attente.
  • Ajouter une interface, un panneau ou un réglage graphique générique.
  • Recevoir des commandes de l’interface en tant que plugin tiers.
  • Compter sur FLAG_HAS_UI ou sur PluginV1.version.
  • Recevoir l’événement seeked (jamais émis).
  • Être rechargé à chaud, remplacé DLL ouverte, ou exécuté hors Windows.

Aucun bac à sable

Une DLL est chargée par LoadLibraryW dans le processus du lecteur. Il n’y a ni signature, ni manifeste de permissions, ni processus séparé. Une DLL peut lire vos réglages et vos fichiers, ouvrir des sockets ou faire planter l’application. La seule protection réelle est de n’installer que du code dont la source est connue.

État de la documentation

Points ouverts

  • Aucun manifeste de plugin : les métadonnées sont compilées dans la table PluginV1. Un manifeste séparé n’existe pas.
  • Aucun en-tête C/C++ n’est fourni : l’ABI est utilisable depuis Rust via la crate, ou reconstruite à la main.
  • Aucun test du chargeur, du pont JSON, des callbacks ou du cycle de vie n’existe dans le dépôt.
  • La compatibilité N−1 n’est pas prévue : l’ABI est strictement égale à 1.
  • La licence du SDK, l’URL de publication et la politique de support restent à préciser.
