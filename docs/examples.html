Exemples commentés

Deux plugins DLL sont réellement présents dans ember-sdk/plugins : listenbrainz et discord. Les extraits ci-dessous en sont copiés, avec leurs commentaires d’origine. Ils montrent les deux contraintes structurantes de l’ABI v1 : ne jamais bloquer le fil de l’interface et tester le contrat avec du JSON réel.

Extraits du dépôt Rust 2021 cdylib hello et remote absents

Deux exemples sur quatre sont disponibles

Le workspace ember-sdk/Cargo.toml déclare encore plugins/hello et plugins/remote, mais ces dossiers ne sont pas présents dans l’arborescence actuelle. Cette page ne reconstitue pas leur code : elle se limite aux sources vérifiables de discord et listenbrainz. Le plus petit plugin complet est reconstruit dans Créer son premier plugin.

Les deux crates sont indépendants, en cdylib, et partagent la même dépendance par chemin vers ember-plugin-api. Le nom de la bibliothèque détermine le nom du fichier .dll, pas l’identité du plugin. 

# ember-sdk/plugins/listenbrainz/Cargo.toml
[package]
name = "listenbrainz-plugin"
version = "1.0.0"
edition = "2021"
description = "Envoi des écoutes à ListenBrainz depuis Ember Player"
license = "MIT"

[lib]
name = "listenbrainz_plugin"
crate-type = ["cdylib"]

[dependencies]
ember-plugin-api = { path = "../../ember-plugin-api" }
serde_json = "1"
ureq = "2"

discord suit exactement la même forme, avec name = "discord-plugin", name = "discord_plugin" et sans ureq : il parle à Discord par un tube local, pas par HTTP.

ListenBrainz : un événement, un envoi

Le plugin ne fait rien dans tick. Il réagit à deux événements : track_started pour « playing now », et played pour une écoute validée par le seuil de l’hôte. Le jeton n’est pas stocké dans plugins.listenbrainz : il reste dans les réglages de premier niveau et arrive par ui_command.

Lire l’événement sans bloquer

fn event(&mut self, event: &str, host: &Host) {
    let v: Value = serde_json::from_str(event).unwrap_or(Value::Null);
    match v["type"].as_str().unwrap_or_default() {
        "track_started" => {
            let meta = Meta::new(
                v["artist"].as_str().unwrap_or_default(),
                v["title"].as_str().unwrap_or_default(),
                v["album"].as_str().unwrap_or_default(),
            );
            host.log(1, &format!("listenbrainz : playing now « {} »", meta.title));
            self.submit(host, meta, None);
        }
        "played" => {
            let meta = Meta::new(
                v["artist"].as_str().unwrap_or_default(),
                v["title"].as_str().unwrap_or_default(),
                v["album"].as_str().unwrap_or_default(),
            );
            let at = v["at"].as_i64().unwrap_or_else(|| {
                std::time::SystemTime::now()
                    .duration_since(std::time::UNIX_EPOCH)
                    .map(|d| d.as_secs() as i64)
                    .unwrap_or(0)
            });
            host.log(1, &format!("listenbrainz : écoute « {} »", meta.title));
            self.submit(host, meta, Some(at));
        }
        _ => {}
    }
}

Points à retenir : le JSON est parsé avec unwrap_or(Value::Null), donc un événement inattendu ne panique pas ; les champs absents deviennent des chaînes vides ; et event ne fait aucun appel réseau direct. Il délègue à submit, qui crée un fil.

Déléguer le réseau à un fil

fn submit(token: &str, meta: Meta, listened_at: Option<i64>) -> bool {
    let token = token.trim().to_string();
    if token.is_empty() || meta.title.trim().is_empty() {
        return false;
    }
    let body = payload(&meta, listened_at).to_string();
    std::thread::Builder::new()
        .name("ember-listenbrainz".into())
        .spawn(move || {
            let agent = ureq::AgentBuilder::new()
                .timeout_connect(std::time::Duration::from_secs(8))
                .timeout(std::time::Duration::from_secs(15))
                .build();
            let _ = agent
                .post("https://api.listenbrainz.org/1/submit-listens")
                .set("Authorization", &format!("Token {token}"))
                .set("Content-Type", "application/json")
                .set("User-Agent", "EmberPlayer/2.6.0 (Slint)")
                .send_string(&body);
        })
        .is_ok()
}

Ce que le booléen signifie vraiment

submit renvoie true si le fil a pu être créé, pas si la requête HTTP a réussi. Le résultat de send_string est ignoré (let _ =) : une erreur réseau, un jeton refusé ou un HTTP 429 ne laisse aucune trace dans plugins.log. C’est un choix « fire and forget » assumé par le plugin, pas un comportement de l’hôte.

Le fil ne touche jamais au Host. Seuls des types purs (String, Meta, Option<i64>) sont déplacés dans la closure. C’est la seule forme sûre avec l’ABI actuelle : Host n’est pas Send et tous les callbacks hôte → plugin arrivent sur le fil de l’interface.

Recevoir le jeton par ui_command

fn ui_command(&mut self, json: &str, host: &Host) {
    let v: Value = serde_json::from_str(json).unwrap_or(Value::Null);
    if v["type"].as_str() == Some("configure") {
        let token = v["token"].as_str().unwrap_or_default().trim().to_string();
        if token != self.token {
            self.token = token;
            host.log(
                0,
                if self.token.is_empty() {
                    "listenbrainz : jeton retiré, envoi inactif"
                } else {
                    "listenbrainz : jeton configuré"
                },
            );
        }
    }
}

Cette méthode n’est appelée que parce que l’identifiant codé en dur est listenbrainz. Un plugin tiers qui implémente la même méthode ne recevra jamais de configure avec l’hôte 2.6.0. Pour un plugin tiers, la configuration doit passer par host.setting / host.set_setting, ou par un fichier que le plugin lit lui-même.

Déclaration et test du format

La macro ne fait que décrire la table PluginV1. Aucun manifeste séparé n’est lu par l’hôte. 

ember_plugin_api::declare_plugin!(
    ListenBrainz,
    id = "listenbrainz",
    name = "ListenBrainz",
    version = "1.0.0",
    desc = "Envoie « playing now » au démarrage et les écoutes validées au seuil d'écoute.",
    category = "Intégration",
    flags = 0,
    deps = "",
);

Le plugin teste la forme du JSON sans lancer l’hôte, ni le réseau, ni Slint. C’est le type de test à conserver dans un plugin tiers : il vérifie le contrat que vous contrôlez, pas les effets de bord.

Discord : canal et fil de travail

Discord Rich Presence exige un dialogue IPC local, des reconnexions et une cadence régulière. Le plugin isole tout cela dans un fil nommé ember-discord et ne communique avec lui que par un canal mpsc. Le fil de l’interface ne fait qu’empiler des commandes.

Le canal et la poignée de main

#[derive(Debug)]
enum Command {
    Set(Option<Activity>),
    Shutdown,
}

struct Client {
    tx: Sender<Command>,
    current: Arc<Mutex<Option<Activity>>>,
    /// Vrai dès que Discord a répondu au handshake (READY).
    connected: Arc<AtomicBool>,
}

impl Client {
    fn new(client_id: &str) -> Client {
        let (tx, rx) = channel();
        let current = Arc::new(Mutex::new(None));
        let connected = Arc::new(AtomicBool::new(false));
        let id = client_id.trim().to_string();
        let worker_current = current.clone();
        let worker_connected = connected.clone();
        std::thread::Builder::new()
            .name("ember-discord".into())
            .spawn(move || worker(id, worker_current, worker_connected, rx))
            .ok();
        Client {
            tx,
            current,
            connected,
        }
    }

current conserve la dernière activité pour pouvoir la réémettre après une reconnexion ; connected permet à tick de journaliser les transitions sans interroger le fil. Le Drop de Client envoie Command::Shutdown, ce qui provoque un dernier envoi avant la fermeture du tube.

Boucle de travail et reconnexion

loop {
    while let Ok(cmd) = rx.try_recv() {
        match cmd {
            Command::Shutdown => {
                flush(&mut pipe, &current, &mut nonce);
                return;
            }
            Command::Set(a) => {
                if let Ok(mut cur) = current.lock() {
                    *cur = a;
                }
            }
        }
    }
    if pipe
        .as_ref()
        .map(|p| !p.alive.load(Ordering::Relaxed))
        .unwrap_or(true)
    {
        pipe = None;
        connected.store(false, Ordering::Relaxed);
    }
    if pipe.is_none() && last_attempt.elapsed() >= Duration::from_secs(5) {
        last_attempt = std::time::Instant::now();
        if let Some(mut p) = open_pipe() {
            let hello = json!({ "v": 1, "client_id": id });
            let _ = p.writer.write_all(&encode_frame(OP_HANDSHAKE, &hello));
            let _ = p.writer.flush();
            pipe = Some(p);
        }
    }
    // … envoi de l'activité courante, puis :
    match rx.recv_timeout(Duration::from_millis(250)) {
        Ok(Command::Shutdown) => {
            flush(&mut pipe, &current, &mut nonce);
            return;
        }
        Err(RecvTimeoutError::Disconnected) => return,
        Ok(Command::Set(a)) => {
            if let Ok(mut cur) = current.lock() {
                *cur = a;
            }
        }
        Err(RecvTimeoutError::Timeout) => {}
    }
}

La boucle tente une reconnexion toutes les cinq secondes, vide le canal sans bloquer (try_recv), puis attend au maximum 250 ms. Aucun appel au Host n’est effectué ici. Le fil ne journalise pas non plus : c’est tick, côté interface, qui observe connected et écrit dans le journal.

Recaler l’horodatage dans tick

fn tick(&mut self, snapshot: &str, host: &Host) {
    // Journalise les transitions de connexion : sans client Discord, la
    // présence reste muette et c'est la seule trace exploitable.
    if let Some(client) = self.client.as_ref() {
        let now = client.connected.load(Ordering::Relaxed);
        if now != self.connected {
            self.connected = now;
            host.log(
                if now { 0 } else { 2 },
                if now {
                    "discord : connecté, présence active"
                } else {
                    "discord : client injoignable, nouvelle tentative"
                },
            );
        }
    }
    let v: Value = serde_json::from_str(snapshot).unwrap_or(Value::Null);
    let playing = v["playing"].as_bool().unwrap_or(false);
    if !playing {
        self.clear();
        return;
    }
    let Some(track) = self.track.as_ref() else {
        self.clear();
        return;
    };
    if track.title.trim().is_empty() {
        self.clear();
        return;
    }
    let Some(client) = self.client.as_ref() else {
        return;
    };
    let pos = v["pos"].as_f64().unwrap_or(0.0).max(0.0);
    let now = std::time::SystemTime::now()
        .duration_since(std::time::UNIX_EPOCH)
        .map(|d| d.as_secs() as i64)
        .unwrap_or(0);
    let started = now - pos as i64;
    let changed = self
        .last_started
        .map(|last| (last - started).abs() > 2)
        .unwrap_or(true);
    if !self.active || changed {
        let album = if track.album.trim().is_empty() {
            "Ember Player"
        } else {
            track.album.as_str()
        };
        client.set_activity(Some(Activity::new(
            &track.title,
            &track.artist,
            album,
            Some(started),
        )));
        self.active = true;
        self.last_started = Some(started);
    }
}

Le plugin ne réémet pas l’activité à chaque tick : il ne le fait que si la présence n’est pas active ou si l’horodatage dérive de plus de deux secondes. C’est un compromis entre la précision affichée par Discord et le nombre d’écritures dans le tube.

Nettoyer sur les événements

match v["type"].as_str().unwrap_or_default() {
    "track_started" => {
        self.track = Some(Track {
            title: v["title"].as_str().unwrap_or_default().to_string(),
            artist: v["artist"].as_str().unwrap_or_default().to_string(),
            album: v["album"].as_str().unwrap_or_default().to_string(),
        });
        if let Some(t) = self.track.as_ref() {
            host.log(1, &format!("discord : piste « {} »", t.title));
        }
        // Le prochain tick recale l'horodatage sur la position réelle.
        self.last_started = None;
    }
    "paused" => self.clear(),
    "resumed" => self.last_started = None,
    "seeked" => self.last_started = None,
    "stopped" => {
        self.track = None;
        self.clear();
    }
    _ => {}
}

La branche seeked est morte

L’hôte 2.6.0 ne construit jamais d’événement seeked. La branche existe dans le plugin, mais elle ne sera jamais exécutée tant que l’hôte n’émet pas cet événement. Le recalage après un seek dépend donc, en pratique, de la dérive de l’horodatage détectée dans tick.

Ce que le plugin ignore volontairement

  • Les erreurs d’écriture dans le tube ne sont pas journalisées : le fil marque simplement le tube comme mort et retentera.
  • Une réponse READY n’est pas validée : tout cadre IPC reçu marque ready.
  • Le chargement de l’identifiant Discord intégré est codé en dur dans la DLL, pas fourni par l’hôte.
  • Le plugin utilise let … else (Rust 1.65+) alors que le dépôt ne fixe aucune version minimale de Rust.

Ce que ces exemples ne montrent pas

Les deux plugins livrés sont volontairement étroits. Ils ne couvrent pas plusieurs capacités que l’ABI expose pourtant, et certaines qu’elle n’expose pas du tout.

SujetÉtat réelOù lire la suite
Réglages persistants Aucun plugin livré n’appelle set_setting ; le compteur du guide est une reconstruction. Guide → code minimal · Host et settings
Panneau ou interface fournie par la DLL Impossible : host.panel est journalisé, FLAG_HAS_UI n’est pas lu. Panneaux et interface
Échantillons audio, bibliothèque, file d’attente Aucune API, ni pour une DLL ni pour un builtin. Capacités réelles

Tests d’intégration avec l’hôte Aucun test automatisé de chargement de DLL dans le dépôt ; les essais restent manuels. Erreurs de chargement

Patron de persistance recommandé

Ce bloc n’est pas un extrait livré : il applique les seules méthodes réelles de Host à un besoin courant. Il doit être adapté et testé avant diffusion. 

fn init(&mut self, host: &Host) -> Result<(), String> {
    let launches: u64 = host
        .setting("launches")
        .and_then(|s| s.trim().parse().ok())
        .unwrap_or(0)
        + 1;
    host.set_setting("launches", &launches.to_string());
    host.log(0, &format!("mon-plugin : lancement {launches}"));
    Ok(())
}

Rappels : la valeur est lue comme du JSON sérialisé ; set_setting n’écrit pas immédiatement sur le disque ; une chaîne contenant un NUL est silencieusement refusée ; et enabled appartient à l’hôte.

Checklist avant de distribuer une DLL

  1. Contract et architecture

    abi_version = 1, export ember_plugin_v1, DLL x64 comme l’hôte. Un id stable, unique et non vide. Les métadonnées vivent dans la table compilée, pas dans un fichier annexe.

  2. Non-blocage

    Aucun accès réseau, disque lent ou boucle d’attente dans init, tick, event ou shutdown. Le travail long part dans un fil ; le fil ne touche jamais au Host.

  3. Erreurs visibles

    Journaliser le détail avant de renvoyer Err depuis init : le texte ne traverse pas la frontière C. Ne pas avaler silencieusement les erreurs réseau sans au moins un compteur ou un log.

  4. Installation et redémarrage

    Copier la DLL dans <exe>\plugins ou %APPDATA%\Floral Player\plugins, puis redémarrer : le scan n’a lieu qu’au démarrage. Vérifier %APPDATA%\Floral Player\plugins.log.

  5. Ce que l’hôte ne fera pas

    Il ne vérifiera pas PluginV1.version, n’affichera pas de panneau générique, n’enverra pas ui_command à un tiers et n’émet pas seeked. Ne concevez pas l’expérience autour de ces fonctions.

Une DLL est du code arbitraire

Aucun bac à sable, aucune signature, aucun manifeste de permissions. Une DLL peut lire les réglages, les fichiers et le réseau de l’utilisateur, ou tuer le processus. La seule protection est la provenance du code.

Points non vérifiables dans l’état actuel

  • Les sources de hello et remote sont absentes : impossible de citer leur code réel.
  • Aucun exemple livré de panneau, de réglage persistant ou d’interface fournie par une DLL.
  • Aucun test automatisé de chargement ou de mise à jour d’une DLL.
  • Le comportement réseau des exemples n’est couvert par aucun test ; seuls les formats JSON le sont.
  • Aucune politique de signature ou de publication des DLL n’est définie dans le dépôt.
